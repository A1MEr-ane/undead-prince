**结论先说：**

- 当前原型自然局（峰值 46–54 个活跃单位）在 1440×900、Debug、M1 上完整帧 **P50 8.5 ms**，大部分帧在 60 FPS 预算内，但 **P99 18–22 ms、max 59–113 ms**，约 1–4% 的帧超过 16.7 ms。尖峰不是渲染，而是破墙时的流场重算。
- 压力档完整帧 P50：**100 单位 10.3–24.4 ms；200 单位 28.8–86.3 ms；300 单位 49.6–179.7 ms；500 单位 110.8–455.5 ms；1000 单位近战 618 ms**。200 单位起绝大多数帧超过 33.3 ms；300/500 档全部帧超过 33.3 ms。
- 无头模拟和完整帧几乎一样：渲染残差 P50 0–4.6 ms、`view.refresh()` 0.11–0.87 ms。**瓶颈在模拟，不在绘制调用**；灰盒阶段 641 个 draw call 不是主因。
- T61 的“200 单位约 7 ms”是旧战斗场景、纯 `_simulate`、无渲染的数字；在攻城原型里 200 单位无头 P50 已是 27.5–75.3 ms，不能外推到完整画面，也不能外推到新原型。
- 最大单帧尖峰是**拓扑变更后的流场重算**：自然局 58–73 个缓存流场时一次破墙 `change()` 要 55–113 ms；56×48 地图上每多一个缓存流场约 +4.7 ms，缓存 175 个时可达 805 ms。其次是 500 单位首次跨区调度，`director.tick` 单次 340 ms。

### 1.2 方法

- 探针直接实例化真实 `res://proto/siege/siege.tscn`（`siege.gd` / `siege_unit.gd` / `siege_director.gd` / `siege_view.gd`），把 `main.set_process(false)`，由探针每个样本执行 **2 个 1/30 s 固定步**（与 60 FPS 目标下的 2 步/帧对齐），再调用 `view.refresh()` 并渲染。
- 窗口模式的“完整帧”是相邻两次 `_process` 开始之间的墙钟间隔，包含模拟、`refresh`、渲染、引擎和 OS；无头模式只计 `main.simulate()` 两部的耗时。“渲染残差” = 帧间隔 − sim − refresh。
- 压力场景用 `main.spawn()` 直接生成精确 N 个单位，并把各兵种 `hp` 放大、`damage/knockback/stun` 归零，保持人数恒定；关闭援军、把攻占时间设到极大、用 `main.won=true` 防止第一步触发全歼结束。**这是规模压力，不是正常经济或死亡曲线。**
- 压力场景的目标重选大多被冻结（`next_target=1e9`）以固定事件序列；`cave` 保留真实洞内逻辑。自然局不注入任何东西，走默认守军、经济、死亡、援军和 `waves` / `main_gate` 机器人，直到自然结束。
- 阶段拆分用 `perf_siege.gd` / `perf_map.gd`：`simulate()` 与父类逐行同序，只在阶段边界加 `Time.get_ticks_usec()`；`perf_map` 用子类包住 `distance` / `direction` / `field` / `change`。同场景、同步数下与父类的 `state_hash` 完全一致。
- 状态哈希 = 所有单位 id/faction/位置/hp/alive + `main.result()` 的 SHA-256；无头和窗口同配置必须相等。36/36 压力/极端对、2/2 自然策略全部相等，见 §2.7。

### 1.3 场景

| 名字 | 内容 |
|---|---|
| `march` | 同路密集行军：N 个亡魂在海岸列队，沿大路走向关闭的城门；后段会堆在门前 |
| `multi` | 多线投放：N 个亡魂分三组从大路/侧路/山洞入口推进 |
| `melee` | 密集近战：50% 亡魂 / 40% 盾兵 / 10% 弓兵在广场混战 |
| `gate` | 窄门争夺：城门打开，60% 亡魂从外侧压入，40% 守军在门内侧防守 |
| `breach` | 破墙瞬间：N 个亡魂攻击城门，门血 50，记录破门样本 |
| `reinforce` | 跨区增援：25% 亡魂在海岸，75% 守军分驻三区，调度层实际派兵 |
| `cave` | 山洞转移：N 个亡魂在洞口排队，容量 2、传送 2.5 s |
| `dawn` | 黎明前高回复：从 282 s 开始，广场混战，夜长 300 s |
| `camera` | 镜头缩放和切换：行军场景，每 75 帧在 25/85 正交尺寸和 0/90/180/270° 间切换（仅窗口） |
| `idle` | 辅助基线：N 个亡魂原地散开，隔离移动/近战，只剩索敌、寻路、分离与占领统计的固定成本 |

### 1.4 限制

- 仅 Debug 编辑器构建；Release 可能更快，但没有导出模板/预设，未测。不要把这里的绝对毫秒当作发行版指标。
- 压力场景冻结目标重选，且单位不死。自然局 50 单位时 `orders` 已占约 41% 的步耗时，所以 200–500 的压力数字可能**低估**真实索敌/重选成本。
- 灰盒单位是一个无光照 BoxMesh；正式精灵的透明层、排序、图集切换和动画会增加 GPU/绘制成本，本轮没有覆盖。
- 单机单次样本，未做置信区间；P50/P95/P99 用最近秩，P99 在 240–600 样本上分别只有 2–6 个样本支撑。max 是单次最大帧，包含 OS 调度噪声。
- 完整帧间隔同时包含 CPU 与 GPU 工作，二者可能重叠；没有 GPU 时间戳，不能把 sim 和渲染直接相加。
- T69 未合入本分支；测量的是 `1fda4ce` 的 T67 原型。若 T69 改 `simulate` 顺序、索敌频率或墙体更新，需要重跑。

## 3. 瓶颈排序

按本轮数据的影响排序（不是按代码行数）：

1. **分离/近邻查询（`unit_tick_move_combat`）**：密集行军/排队/破门场景占步耗时 47–95%。500 单位 march 均值 154.47 ms/步、峰值 354.76 ms/步。`separation()` 对每个单位扫描两个阵营的邻近格，局部密度高时是 O(N×邻居数)，这是 300–500 档的主要墙。
2. **索敌/方向（`sense_nearby`）**：密集近战/窄门 500 单位占 49–56%（56.01 / 52.91 ms/步）。`siege_unit.gd:129` 每个模拟步都对每个单位调用一次 `terrain.direction()`（不在 `next_sense` 节流内），`nearest_enemy()` 又在密集格子里扫大量候选。自然局 50 单位时还只占 15%，人数一多就变成主项之一。
3. **目标选择/路径（`orders`）**：自然局 50 单位时 1.20 ms/步（约 41%），是自然局最大的单项；压力场景为了固定人数/事件大多冻结了它，所以 200–500 的压力数字低估了真实重选成本。500 单位真实索敌大概率比 §2.3 更贵。
4. **拓扑变更流场重算（`siege_map.change`）**：自然局 55–113 ms/次，微基准 4.7 ms/缓存流场、175 个流场 805 ms。这是**最大单帧尖峰**，也是玩家破墙时最不能接受的一次卡顿。
5. **流场构建（`field`）**：4.2–11 ms/个；自然局 58–73 个新流场分布在全场，单个 `sense` 步可能吃到 20–42 ms 的尖峰（gate 100 的 `sense max` 42.14 ms）。多个单位同帧请求新目标时会叠加。
6. **调度（`director.tick`）**：自然局最大 18.6–19.0 ms；500 单位压力下首次派兵 340 ms。派兵 donor 排序、`terrain.distance()` 与流场构建同帧，是跨区增援场景的尖峰来源。
7. **占领统计（`update_captures`）**：500 单位 2.1–2.9 ms/步，约 3%。4 个区 × 全部单位扫描，量级不大但可以零成本修掉。
8. **渲染/绘制调用**：完整帧残差 P50 0–4.65 ms，`refresh` 0.11–0.87 ms，draw call 241/341/441/641（100/200/300/500；1000 为 march 1141、melee 1241），static memory 133/139/144/155/183 MB。灰盒阶段不是主瓶颈；正式精灵透明层会额外增加，但本轮不能给出那部分数字。

## 4. 对旧数据和审查第 5 节的回答

- **“200 单位约 7 ms”**：T61 报告写的是旧战斗场景的 `_simulate` 均值 6.93 ms（无渲染、不死单位、岛心铺开）。它不是攻城原型，也不是完整帧。本次攻城原型 200 单位无头 P50 是 27.5–75.3 ms；完整帧 28.8–86.3 ms；最轻的 idle 200 也有 23.1/26.5 ms。7 ms 这个数量级不能外推到新原型或完整画面。
- **完整帧是否等于模拟 + 渲染？** 不完全是。自然局 50 单位时 sim 3.4 ms、frame 8.5 ms，渲染/引擎残差约 4.6 ms；高负载时 sim 占绝对多数，GPU 工作与下一帧 CPU 重叠，残差看起来接近 0。不能把两者简单相加。
- **60/30 FPS 预算**：60 FPS 约 16.7 ms，30 FPS 约 33.3 ms。当前灰盒自然局 P50 8.5 ms，但有 1–4% 的帧超 16.7 ms；100 单位只在 idle/multi/reinforce 等稀疏场景边缘通过，密集场景 17–24 ms；200 单位起基本没有 60 FPS 余量，300/500 连 30 FPS 都不满足。
- **哪些场景最贵**：march（堆门）451 ms、camera 455 ms、cave（洞前排队）449 ms、breach（堆门）396 ms、gate 217 ms、melee 205 ms、dawn 225 ms（500 单位 P50）。`reinforce` 500 的 P50 只有 132 ms，因为单位分散在四个区，但它有 342 ms 的调度尖峰。
- **能不能直接上 300/500**：按本轮数据，不能。300 单位完整帧 P50 50–180 ms、500 单位 111–455 ms；在优化分离/索敌/流场之前，建议把灰盒压力上限控制在 100–150，并优先做局部查询和流场重算的工程改造。
