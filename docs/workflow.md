# 多智能体工作流：Claude + Codex + DeepSeek Harness（2026-11-24）

依据：用户的《工作流决策简报》、仓库现状、本机实测。通用规则（分支、报告模板、已知坑）见 `docs/collab.md`；本文只讲**谁做什么、怎么自动化、怎么衡量**。

## 0. 结论（2026-11-24 更新：用户《委派与额度优化指令》，主旨是节省 Claude 额度）
- **Claude 只管"做什么、为什么、效果对不对"**：玩法、剧情、系统设计、总体规划、关键架构决策、美术方向与关键视觉验收、最终集成决策。
- **Codex 是工程主力**：功能实现、Godot 渲染与着色器、UI 实现、工具链、技术方案细化与任务拆分、代码审查、疑难 bug、全部图像生产。拿到的是**完整工作包**，自己读代码、定实现、拆子任务、测试、修复。
- **DSH 在谷时跑批量**：规格已定的 Blender 批量建模与导出（先通过能力验证）、批量测试、日志分析、常规修复、重复性开发。
- **本地脚本**：编译、测试、资产规格、导入检查、任务队列、定时启动、状态更新。能用程序判定的不花模型额度。
- 验收标准由 Claude 定并固化成脚本（`tools/verify/verify.sh`），执行者不能改阈值。
- 这是默认路由，不是能力排名；按实际质量、返工、剩余额度和现金支出调整。不为了用满三个模型而拆任务，也不让同一任务默认经过三个模型。

## 1. 对简报前提的修正（实测或读代码得出）
| 简报里的假设 | 实际情况 | 影响 |
|---|---|---|
| 单位是 3D 模型，要验 GLB 重导入、骨骼动作 | 单位是 **Blender 渲染的 2D 精灵**（RG=部位坐标、B=明暗、A=覆盖度），Godot 里只吃图集 PNG + JSON | 验收改成：图集格式、帧布局、`validate.py`、游戏内可读性截图 |
| DSH 可以直接无人值守 | 无头 profile 默认只走 API 密钥并关闭账号模块；加 `--patch tools/agents/dsh-account.patch.yml`（参考 dsh-baton）后**复用桌面版账号登录**，实测可用 | 不需要另配密钥；计费以账户后台账单为准 |
| DSH 能看图 | 未验证；默认模型 deepseek-flash，是否支持图像输入不确定 | 先假设**不能看图**：DSH 的活必须能用脚本判断对错 |
| Codex 能独立完成并提交 | 沙箱里**打不开 Godot 窗口、经常提交失败** | Codex 交付后由 Lead 截图验收、补提交 |

## 3. 任务路由与 Claude 的介入边界
1. 需要设计判断、审美判断、改验收标准或核心接口 → Claude 决定，写进 docs；实现仍派出去。
2. 完整、可独立交付的工程或图像工作包 → **Codex**。Claude 只写目标、约束、依赖、allowed、验收标准，不写实现细节。
3. 规格明确、可重复、能用脚本判对错、不急 → **DSH 谷时队列**（可由 Codex 的工作包继续下派）。
4. 改几行、委派和审核成本明显高于直接做的小事，或必须由 Claude 处理的紧急问题 → Claude 直接做。
- Claude **不**逐步指导执行、不监视进程、不逐轮读日志、不审批常规修复；不重做已通过验收的工作。
- 并行前提不变：`allowed` 不重叠；`scripts/main.gd`、`project.godot` 的接入改动写在工作包里明确授权给一个执行者。

### 分级验收
1. **程序检查**：`verify.sh`、资产规格、导入、文件完整性。
2. **技术一级审核**：Codex 按需审 DSH 产物和异常结果；自动验收通过的简单任务不必再审。Codex 的高风险变更由独立审查者复核。
3. **Claude 审核**：只看需要设计判断的部分、关键视觉样张（首件）、重大架构或集成风险。成熟批量资产在首件通过后**抽样**审；用户要求的批次审批照常保留。

### 摘要优先
- 执行者交付时在报告开头给出结构化摘要（格式见 `docs/collab.md` 第 4 节）。Claude 默认只读摘要、关键差异、必要预览和 `needs_claude: true` 的事项。
- 完整日志留在本地，只在调查异常时按范围读取。Claude 不定期轮询、不重复汇总、不重读整个仓库。

### 升级给 Claude 的条件（只有这些）
- 需要调整玩法、剧情、美术方向、核心接口或验收标准
- 规格冲突或缺失，执行者无法在授权范围内决定
- 达到重试或预算上限，需要重新拆分或改方案
- 重大集成、安全、数据或架构风险
- 需要关键审美判断或用户审批

### 额度控制
- Codex：积极使用订阅额度，承接此前由 Claude 做的实质性工程任务。
- DSH：只在经核实的谷时窗口跑付费任务；没有有效凭据或预算不启动；未经用户授权不扩大预算。
- 按服务分别记录：首次通过率、返工次数、墙钟时间、Claude/Codex 额度变化、DSH 实际支出（`reports/metrics.csv`）。交接或返工成本明显上升时，改规格或缩短链路，不加智能体。

## 4. 自动化架构（最小可用，已落地的打 ✓）
```
tasks/Txx-*.md        任务卡（front matter：owner、branch、worktree、allowed、verify、retry_limit、escalate_if）  ✓ 模板
TASKS.md              看板（一行一任务，指向任务卡）  ✓
tools/agents/run_agent.sh   按任务卡建 worktree、启动 codex/dsh、写日志、记指标  ✓
tools/verify/verify.sh      固定验证套件：parse / battle（多种子无头对战，输出 RESULT JSON）/ sprites（Blender validate.py）  ✓
reports/agents/<id>.md      执行者交付报告；<id>.log 原始日志（Lead 只看报告和 verify JSON，不读全日志）
reports/verify/*.json       每次验证的结构化结果（不入库）
reports/metrics.csv         每次执行一行：耗时、退出码、用量、是否交报告  ✓
tools/agents/offpeak.sh / run_queue.sh   谷时判断与 DSH 队列  ✓（launchd：`~/Library/LaunchAgents/com.undeadprince.dsh-queue.plist`，每天 12:01、18:01；工程必须在 ~/Documents 之外，否则 macOS 不让后台任务访问）
```
流程：Claude 写任务卡 → `run_agent.sh` 启动 → 执行者在分支提交 + 写报告 → Claude 读报告和 verify JSON → 视觉项看截图 → 合并到 main → 再跑一次 `verify.sh all`。

## 5. 盾兵试点（端到端）：落地顺序与验收
目标：从三视图出发，做出第一个"按概念图建模 → 渲染精灵 → 在游戏里跑"的兵种，并测出流程的真实成本。

| 步骤 | 谁 | 做什么 | 验收 |
|---|---|---|---|
| P1 | Claude | 写**兵种资产规格**（`assets/specs/k2_shieldman.yml`）：比例（头身比）、部件清单、部位贴图分区、配色、剪影特征、三角面预算、动作清单（沿用 T06 的 11 个动作和时长） | 规格能被脚本读取 |
| P2 | Codex | 把 T06 的 `build_swordsman.py` 改成**按规格建模**；参照三视图做盾兵低模；`render_sprites.py` 出图集；手绘部位贴图（王国蓝白、太阳纹章盾） | `validate.py` 通过；预览图给 Claude |
| P3 | Claude | 把 T06 图集格式接进 Godot（着色器读 4×4 部位分区、Unit 按 JSON 的动画表播放），盾兵替换现有程序化精灵；重做走路时序 | `verify.sh all` 通过 + 游戏内截图（远景/近景）由 Claude 判断可读性 |
| P4 | Codex 与 DSH 各做一次 | 用同一份规格格式做**民兵**（换部件和配色） | 同一套验收；对比两边的首次通过率、重试次数、耗时、用量 |
| P5 | Claude | 根据 P4 数据定下"规格→资产"这类活以后交给谁 | 写进本文第 2 节 |

潜在阻碍：T06 的部位分区（每外观 4×4 区域）与当前游戏着色器（codex/sprites 的格式）不同，P3 要统一成一种；DSH 未配密钥前 P4 只做 Codex 一边。

## 6. 成本与质量监控
- 每次执行自动写 `reports/metrics.csv`：日期、任务、执行者、退出码、墙钟时间、用量（Codex 日志里的 tokens used；DSH 的 `--json` 事件）。
- Claude 在合并时补两列（手工）：**首次是否通过验收**、**人工介入次数**。
- 每周（或每 10 个任务）汇总一次：按执行者算 *每个合格产出的平均墙钟时间、重试次数、用量、返工率*；据此调整第 2 节的分工，而不是按模型名固定。
- DSH 的真实账单以 DeepSeek 后台为准。
- **谷时（2026-11-24 核实官方价格页 api-docs.deepseek.com/quick_start/pricing）**：高峰 = 工作日 UTC 01:00–04:00、06:00–10:00（北京时间 09:00–12:00、14:00–18:00）；其余时间（含周末和中国法定节假日全天）为谷时，价格为高峰的一半。deepseek-flash（DSH 默认模型）标注支持看图，deepseek-v4-pro 不支持。
- **规则：DSH 只在谷时运行**。`tools/agents/offpeak.sh` 判断时段；`run_agent.sh` 在高峰拒绝启动 DSH（`FORCE=1` 可强制）并把任务时长截到本段谷时结束前 5 分钟；`run_queue.sh` 在谷时依次执行 owner=dsh、status=queued 的任务卡。

## 6.5 额度用尽的处理（2026-11-24 实际遇到）
- Codex 订阅额度按约 5 小时窗口计算；用尽时日志出现 `usage limit … try again at HH:MM`，任务在中途停下，工作区留有未提交改动。
- 处理：指标表记 `quota`；任务卡追加"续作说明"（让下一次先看 `git diff` 接着做）；到恢复时间自动重派。
- 路由调整：Codex 额度紧张时，**能等谷时的活转给 DSH，急的由 Claude 做**；出图类大批量任务（一次几十张）要避开 Codex 正在做的开发任务，错开窗口。

## 6.6 外部工具评估（2026-11-24）
| 项目 | 结论 |
|---|---|
| dsh-baton（MCP：Claude/Codex → DSH，带证据回传和只读复核） | 维护活跃；**暂不安装**——它会自动改写 `~/.claude.json`、`~/.codex/config.toml`，默认自动批准交接任务里的操作。只借用它的账号登录 patch。等需要"Claude 会话里直接交接给 DSH 并等结果"时再评估安装 |
| dsh-plugin-nonurgent（DSH 内的谷时队列） | 不用：只能在 DSH 界面里加任务，外部不能驱动；8 月后未维护；高峰规则没区分工作日 |
| game-dev-dsh-skill | 不用：面向 3D/GLB→网页导出，和本项目的 2D 精灵管线不符；安装脚本 rm -rf，带公网隧道 |

## 6.7 第一次试点数据（2026-11-24）
| 任务 | 执行者 | 次数 | 墙钟 | 用量 | 首次通过 | Lead 介入 | 备注 |
|---|---|---|---|---|---|---|---|
| T17 盾兵建模渲染 | Codex | 4 | ≈ 25 分钟（实际执行） | ≈ 38.5 万 token | 否 | 3 | 1 次因 Lead 规格错误上报；1 次额度用尽；1 次视觉退回（盾太大，Lead 规格问题）；第 4 次通过 |
| T20 能力冒烟 | DSH | 1 | 1.5 分钟 | ≈ 1.3 万（另 17 万缓存读） | 是 | 0 | 命令行、验证、开窗截图、看图都可用；提交不可用 |
| T21 10 种子平衡统计 | DSH | 1 | 14.5 分钟 | 未单独汇总 | 是 | 0 | 报告质量高，给出可验证的假设；顺带发现种子不可复现、新 worktree 需导入 |
| T22 状态树单元测试 | DSH | 1 | 4 分钟 | 未单独汇总 | 是 | 0 | 56 个断言，指出 on_empty 语义与规格措辞不一致 |

初步结论（样本小，继续观察）：
- **DSH 比预期强**：能开窗截图并看图；测试、统计分析、窄范围代码任务首次即通过。可以承担更多"能自动验收"的开发任务，而不只是跑测试。
- **Codex 返工主要来自 Lead 的规格质量**：规格要写成可测量的数值，并配"以参考图为准、偏差 10% 内不上报"的规则；视觉要求要写出"侧视必须露出什么"。
- **出图和建模类任务需要视觉验收回合**：预算按 2–3 轮考虑。
- 用量记录：Codex 读日志里的 tokens used；DSH 需要从 `--json` 事件累加 usage（待在 run_agent.sh 里补上）。
