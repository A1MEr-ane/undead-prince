# 玩法、美术、程序三线对齐（2026-11-28）

- 起因：用户指出 Claude 过于冒进，没弄清需求就开工；玩法、美术、程序互相关联，应先对齐三者的进度，再做整体规划。
- 本文只陈述现状、依赖关系和待决事项，不派新任务。
- 已暂停 T82（小兵形象与 Blender 管线）。它依赖兵种清单、镜头和局内画面，这三样都还没定。
- T80（行为场景测试）和 T81（行动逻辑修正）继续跑。理由：用户已经明确"现阶段只需要解决行动逻辑"，这两个任务只改攻城原型。

## 1. 三条线的现状（事实）
### 玩法
| 已定 | 已做出来、但用户没亲手验收 | 未定 |
|---|---|---|
| 冥火原子化部署；夜战 5 分钟；两种胜利（全歼、攻占后守军撤离）；自然地形不可破坏；城墙可破；守军跨区支援；四个强化方向加渡魂人馈赠；只解决行动逻辑，不测胜率 | 灰盒攻城原型（T67/T69/T74）：部署、冥火、守军调度、刺客、巨人、破墙、山洞；战区固定视角原型（T70） | 镜头方案；击杀收益；部署区是否扩展；攻城失败的后果；第一批正式兵种；地图是否重新设计；冥火曲线 |

**最大的缺口**：核心玩法还没有经过用户亲手试玩并给出判断。自动数据只能看出 bug，看不出好不好玩。

### 美术
| 已定 | 已产出 | 缺口 |
|---|---|---|
| 立绘：精炼墨线；结局：史诗厚涂、不放文字；UI 原则（克制、细金线、三种转场）；局内：3D 地形加朝向镜头的精灵、墨线、阵营边光 | 15 个人物立绘；9 张结局图（E06 不合格）；8 张剧情插画；设定集；Q 版兵种阵容图（2D 概念） | **局内画面从来没在引擎里按目标风格做过**。玩家 90% 的时间看的是战场，而目前战场只有灰盒色块，以及最早那版 Bad North 式的盾兵精灵 |

### 程序
| 部分 | 状态 |
|---|---|
| 主工程 `scripts/` | Bad North 式的"小队加点地下令"战斗（旧操作模型），加上远征航图、回溯、结局框架（T28/T29） |
| 攻城原型 `proto/siege/` | 新玩法模型（原子化部署、自主单位、守军调度），灰盒画面，独立于主工程 |
| UI 动效原型 `proto/ui_motion/` | 占位图形，等用户试手感 |

**结构问题**：新玩法写在原型里，主工程的战斗还是旧模型，两套代码在分叉。迟早要决定原型怎么并入主工程。

## 2. 三者之间的依赖
```
镜头方案 ──┬─> 战场地图怎么设计（每个战区怎么构图）──> 地形和建筑美术
           └─> 小兵要几个方向的精灵 ──> 精灵管线和工作量
兵种清单 ──┬─> 行动逻辑（每个兵种的行为）
           ├─> 动作清单 ──> 精灵管线 ──> DSH 批量建模
           └─> 守军构成和地图上的阵地
战场规模 ──> 同屏单位数 ──> 性能 ──> 精灵和特效的预算
冥火经济、部署规则 ──> 部署 UI 和 HUD
世界观（夜战、永昼） ──> 局内光照（夜色、黎明、王都的人造光）
```
结论：**镜头**和**兵种清单**是两个上游决定。它们不定，地图、美术、精灵管线都会白做。

## 3. 建议：用一个"纵切片"把三条线对齐【议】
纵切片指的是：一张战场，从头到尾做到接近成品的样子，用它同时检验玩法、美术、程序。
- **范围**：
  - 1 张中型战场，3–4 个战区。
  - 亡灵 3 种：普通亡魂，加两种功能兵种。
  - 守军 3 种：盾、弓、骑。
  - 一夜 5 分钟。
  - 最基本的部署 UI 和 HUD。
- **玩法**：行动逻辑通过 B01–B12 场景测试；用户试玩，判断"好不好玩、看不看得懂"。
- **美术**：
  - 局内画面按目标风格：墨线小兵、阵营边光、暗调地形、夜到黎明的光照。
  - 只做这张图需要的模块和 6 个兵种。
- **程序**：
  - 决定原型怎么并入主工程。
  - 性能在这张图的规模下达标。

## 4. 决策顺序（每一步都由用户确认后才往下走）
| 关口 | 需要用户做什么 | 它决定什么 |
|---|---|---|
| G1 | 试玩现在的攻城原型（战区视角版，约 15 分钟），按第 5 节的问题给出感受 | 核心玩法保留、调整还是推翻 |
| G2 | 选镜头：战区固定视角，或自由旋转 | 地图怎么设计、精灵要几个方向 |
| G3 | 定纵切片的兵种：亡灵 3 种、守军 3 种 | 行动逻辑、动作、精灵的范围 |
| G4 | 验收一张**引擎里的**局内风格样张：Codex 用占位精灵把一个战区做成目标画风 | 局内美术方向，之后才开始批量做精灵和地形 |
| G5 | 定原型和主工程的合并方式 | 后续程序结构 |

G1–G3 都确认之后，才恢复 T82（精灵管线）和 DSH 的批量建模。
